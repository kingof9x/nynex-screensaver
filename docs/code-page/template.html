How the code works

Inside nynex, one file at a time

The main page explains the ideas. This page shows how they are written: the Rust code that turns a photo into an animated scene, runs the slideshow, and gets frames onto a Windows or Wayland screen. Every code excerpt below is copied straight from the source, with a link to the exact lines.

You don't need to know Rust to follow along. Where the code uses a Rust idea that matters, the text explains it. If you only want the big picture, the tour on the main page is shorter.

1

The map

nynex is a single Rust program of about 5,400 lines in eleven files under src/. It has no GPU code, no shaders and no game engine: every frame is computed by the CPU into a plain array of 32-bit numbers, one per screen pixel, and handed to the operating system to show.

FileLinesWhat it does
scene.rs2,068The renderer. Analyses a photo once (sky, lake, palette, sun), then draws its frames.
player.rs406The slideshow: timing, loading the next photo in the background, the seven transitions.
saver.rs500Windows of any kind (screensaver, preview box, plain window, Windows wallpaper) and frame timing.
layer.rs406The Linux wallpaper: one Wayland layer-shell surface per monitor.
wallpaper.rs217Windows: putting windows behind the desktop icons; start with Windows.
install.rs110Windows: registering nynex.scr as the screensaver.
omarchy.rs129Linux: the Omarchy screensaver hook, idle time, start at login.
config.rs401Settings: the data types, loading, clamping and safely saving config.json, importing photos.
settings.rs655The settings app, built with the egui toolkit.
main.rs176Startup, the command line, and the --render tool.
stress.rs287Stress tests; only compiled for cargo test.

Two types do almost all of the work, and the rest of the program is plumbing around them:

  • Scene (in scene.rs) is one photo prepared for one screen size. It is built once, which is slow (tens of milliseconds), and then asked for a frame 30 times a second, which is fast (a few milliseconds).
  • Player (in player.rs) owns the scene on screen and the one coming next, decides when to switch, and blends between them. Every screen has its own Player.

The window code only ever does one thing with a player: "here is a pixel buffer and the time since last frame, fill it in and tell me what changed". That single call, Player::update_damage, is the same for the Windows screensaver, the Linux wallpaper and the settings preview.

2

Starting up

Windows starts a screensaver with odd arguments: /s to show it, /p 1234 to draw inside the little preview box of window handle 1234, /c for settings, and sometimes with a colon (/p:1234) or a dash instead of a slash. main strips the slash or dash, splits off anything after a colon, and then picks the job:

{{dispatch}}

Before that, two settings are made that affect the whole run. First, glibc (the C library on most Linux systems) normally gives every thread its own memory pool, called an arena, and is slow to hand freed memory back to the system. A program that decodes a 30 MB photo on a fresh thread every minute ends up with several half-empty arenas. Limiting it to two keeps that in check. Second, the thread pool that draws frames in parallel (the rayon library) is capped at four threads:

{{startup}}

The cap is there because rayon's idle workers spin for a moment before they sleep, hoping for more work. A screensaver finishes its frame in a few milliseconds and then has 30 ms with nothing to do, so extra workers mostly add spinning. Measured, more threads made each frame slightly faster but cost more CPU in total.

The panic hook set just above this writes any crash to crash.log in the settings folder, because a screensaver has no console to print an error to.

3

Loading a photo

load_source turns a file into pixels. GIFs keep their frames (within a 192 MB budget, so a long GIF can't exhaust memory). Stills are decoded, and anything bigger than 2,560 px is shrunk right away, since the grid is never wider than that.

{{load_source}}

Three details worth noticing:

  • decode_unlimited (in config.rs) lifts the image library's default size limit, which refuses very large photos, but sets a 2 GB allocation ceiling of its own instead, so a malicious file that claims to be a billion pixels wide is still refused.
  • into_rgb8 hands the decoded pixels over without copying them when they are already 8-bit RGB, which is the normal case for JPEGs. Its sibling to_rgb8 would briefly hold a second full copy.
  • The result is wrapped in an Arc, a reference-counted pointer, so several monitors can share one decoded photo. It is dropped as soon as every scene built from it is ready.

4

The grid

The core idea of the renderer is to work on a small picture and enlarge it at the very end. Scene::new starts by deciding how small. The pixelation slider (0 to 1) becomes a "big pixel" size of 1 to 16 screen pixels at 1080p, scaled with the screen height so a 4K screen shows the same picture, not a finer one:

{{pixel_size}} {{grid}}

At the default setting a 1080p screen gets a grid about 270 cells wide and 152 tall: 41,000 cells instead of 2 million pixels. Everything that animates is computed on those cells.

Notice also the analysis copy, 320 pixels wide. Finding the sky and the lake doesn't need the full grid; doing it on a small fixed size keeps Scene::new fast whatever the screen, and the results are scaled onto the grid afterwards. The 16.min(sw) in the clamp is a fix from this review: Rust's clamp panics if its lower bound is above its upper bound, which happened when a window was dragged narrower than 16 pixels.

5

Finding the sky

Clouds and stars should only appear in the sky. find_sky works out which cells are sky without any idea what a sky looks like, using two observations: skies are at the top, and skies are smooth.

  1. Texture. For each pixel, the standard deviation of brightness in the 5 × 5 square around it. Sky, haze and still water score low; trees, rock and buildings score high. It is computed with box blurs, using the identity variance = mean of squares − square of mean, so it costs a few passes over the image instead of 25 reads per pixel.
  2. A threshold that adapts. The limit is three times the median texture of the top three rows (plus a small floor). A hazy sky and a crisp one both work, because the limit is measured from the picture itself.
  3. Flood fill from the top. Every smooth pixel on the top row starts as sky. The fill spreads to each neighbour that is also smooth and within a small colour distance of the pixel it came from, so it follows gradual sky gradients but stops at a horizon.
  4. Fill the holes. A second fill runs from the bottom edge through everything that isn't sky. Whatever that second fill can't reach is enclosed by sky (a cloud, the sun, a bird), so it counts as sky too.
{{find_sky}}

The queue is a VecDeque, so this is a breadth-first fill: it spreads outward in rings, which is exactly what the demo on the main page animates. y.wrapping_sub(1) turns "row −1" into a huge number that fails the ny < h check, which is a compact way to skip neighbours off the top or left edge.

6

Finding a lake

A lake reflection means the picture below some row is roughly the picture above it, upside down. find_water_line tests every candidate row between 30% and 90% of the height:

  • Each row's brightness is turned into deviations from that row's average, so a darker reflection still matches a brighter original.
  • For a candidate row y, it correlates row y−1 with y+1, y−2 with y+2, and so on (the mirror), over a band up to a quarter of the image tall.
  • It also correlates the same rows without flipping. Fog, a plain wall or a uniform field look similar everywhere, so they score well both ways. Only a real reflection scores much better flipped.
  • The score is mirrored − max(plain, 0). The best row wins if it scores over 0.5; otherwise there is no lake.
{{find_water}}

The correlation sums are kept in 64-bit floats (f64) because they add up tens of thousands of products, where 32-bit floats would start to lose precision.

7

The palette

Grading

Before choosing colours, every pixel goes through grade: a 25% saturation lift, an S-shaped contrast curve, and a split tone that pushes shadows toward plum, mid-tones toward clay and highlights toward cream. That is where the warm look comes from. The palette entries are then pulled onto three hand-picked colour ramps (clay, slate blue, sage) by fm_color, which chooses a ramp from the hue of the original, ungraded colours, so green grass lands on the sage ramp instead of being warmed to brown.

Choosing the colours: k-means

kmeans_palette samples about 8,000 pixels, starts with k colours spread evenly from darkest to lightest, and then 12 times over assigns each sample to its nearest colour and moves each colour to the average of its samples. Starting from a brightness ramp (instead of random picks) makes the result the same every time and avoids two colours starting on top of each other.

{{kmeans}}

The lookup table

Every frame, each of the 41,000 cells needs "the nearest palette colour". Searching 16 colours for each one would be 650,000 distance calculations per frame. Instead, Scene::new rounds each colour channel to 5 bits (32 levels), which gives 32 × 32 × 32 = 32,768 possible colours, and works out the answer for each one in advance. Each answer is one byte (a palette index), so the table is 32 KB and fits in the CPU's fast cache.

{{lut}}

The index is built by shifting: red's 5 bits go in the top, then green, then blue (r << 10 | g << 5 | b). dither_step is the typical gap between neighbouring palette colours, which sets how strong the dither needs to be to hide the steps between them.

8

Randomness without dice

Nothing in a frame uses a random number generator. A generator has state: each call changes it. If four threads drawing four strips of the screen shared one, they would have to take turns, and the picture would depend on which thread got there first. Instead every "random" decision is a hash of where and when:

{{hash2}}

The same (x, y, seed) always gives the same number between 0 and 1. A sparkle's position is hash2(k, cycle, seed), where k is which sparkle and cycle counts how many times it has twinkled, so it jumps to a new place each time it fades out. The "wrapping" operations tell Rust that overflowing the integer is intended; normally it would be treated as a bug.

Noise for clouds

Hashing whole-number grid points and blending smoothly between them gives value noise: a soft, blobby random field. wnoise also wraps around every period cells in x, so clouds can drift sideways forever without a seam:

{{wnoise}}

Real clouds have big shapes with smaller detail on top. wfbm ("fractal Brownian motion") stacks four layers of noise, each twice as fine and half as strong as the last:

{{wfbm}}

There is one random generator in the program, used only while building a scene to place stars, dust motes and birds. It is seeded from the landscape and the monitor, so the same photo on the same screen always looks the same. It is an xorshift generator, which has the quirk that a state of zero stays zero forever, hence the .max(1):

{{rng}}

9

One frame

Scene::render_damage(t, out, out_has_last) draws the scene at time t seconds into the screen buffer out. The last argument says whether out still holds this scene's previous frame, which lets it redraw only what changed. It returns the list of changed rectangles, or None for "treat the whole frame as new". In order:

  1. GIF frame. For an animated GIF, copy the frame for time t into the scene's starting grid.
  2. Build the grid. If nothing in the scene moves, reuse the cached grid and redraw only the sun glow's rectangle. Otherwise run build_grid: water, clouds, glow, glints, stars, logo, birds, motes, wind streaks, and then stylize.
  3. Sparkles on top of the grid. They come after the palette step so they stay crisp instead of being dithered.
  4. To the screen. Either scale the grid up with hard edges (upscale), or draw text cells (ascii) whose characters follow the brightness underneath.
  5. Breakthroughs on top: torn bands showing source code, a hex dump or a fake crash log.

Colours are [f32; 3] (three floats from 0 to 255) while effects are being added, so blends don't lose precision, and packed into one u32 as 0x00RRGGBB for the screen. That packed layout is what both softbuffer (Windows) and Wayland's XRGB8888 format expect, so the finished buffer goes to the screen without conversion.

10

The moving parts

build_grid starts each frame from a fresh copy of the graded photo grid and adds the effects in order. The water is the simplest to read and shows the pattern most of them follow: work row by row, in parallel, with the effect computed from the row number and the time.

{{water}}

par_chunks_mut(gw) splits the grid below the waterline into rows and hands them to the thread pool. Each row is shifted sideways by the sum of two sine waves moving at different speeds in opposite directions, so the pattern never visibly repeats. Deeper rows get a bigger amplitude. Pixels pushed off one edge come back on the other (rem_euclid is a remainder that is never negative), so no pixels have to be invented.

The other effects, briefly:

  • Clouds are computed on a coarser grid (at most 240 wide), because they are soft and a coarse grid looks the same. Noise is shifted by drift each frame, kept to a band above the horizon, and turned into cloud only where it is above a threshold set by the clouds slider. The result is blended onto sky cells only, by bilinear interpolation.
  • The sun glow exists if the analysis found a clearly brighter spot in the sky. It blends the sky around that spot toward a warm white, with a strength that rises and falls on a six-second sine (glow_k).
  • Glints on the water, stars at night and motes of dust were placed once by the seeded generator; each frame only computes their brightness from the time and their own phase.
  • Birds are five cells in a V, drawn in the darkest palette colour. Each one loops across the sky about every 40 seconds (faster with more wind), bobs gently up and down, and flips between two wing poses twice a second.
  • The logo (optional) is a coverage mask scaled onto the grid and blended toward cream, with an optional darker outline found by checking which cells touch the logo's edge.
  • Wind streaks appear when the wind slider is past 0.4: short bright dashes racing across.

11

Stylize and scale up

Snapping to the palette with a dither

Each grid cell is nudged by a value from a 4 × 4 Bayer matrix, rounded to 5 bits per channel, looked up in the table, and then blended toward that palette colour by the stylize amount:

{{bayer}} {{stylize}}

The Bayer matrix orders the 16 thresholds so that neighbouring pixels get very different nudges. A smooth gradient that would have snapped to the same palette colour over a wide stripe instead flips back and forth in a fine regular pattern, and the eye averages it back into a gradient. #[inline] asks the compiler to paste these small functions into their callers, since they run tens of thousands of times a frame.

Scaling up

The last step makes the screen image from the grid. Each screen pixel takes the colour of the grid cell it falls in ("nearest neighbour"), which keeps the big pixels hard-edged.

{{upscale}}

Two tricks keep this cheap. xmap is a list computed once per scene that says, for every screen column, which grid column it shows, so the inner loop is a table read rather than a division. And because a big pixel is several screen rows tall, most screen rows are identical to the one above: those are copied whole with copy_within, which compiles to a memcpy. The screen is split into bands of 16 rows, one band per task, so the four threads share the work.

Text and breakthroughs

The ASCII look divides the screen into square cells (16 × 16 pixels at 1080p, 32 × 32 at 4K), reads the grid colour at each cell's centre, picks a character from " .:-=+*#%@" by its brightness, and draws it in a brighter version of that colour on a dark version of it, using a built-in 8 × 8 bitmap font scaled up to the cell size. Glitches flip short runs of cells to random symbols for a ninth of a second.

Breakthroughs show text that the program carries inside itself. include_str! is evaluated by the compiler: it pastes the contents of those files into the binary as text. At run time the program splits them into lines once and keeps them:

{{code_lines}}

OnceLock makes that first-time setup safe even if two threads ask at once. The hex dump view reads the bytes of scene.rs the same way. The fake crash log invents its messages, but the file names and line numbers it prints are real positions in that embedded source.

12

Drawing less

The cheapest frame is the one you don't draw. A scene is "still" when nothing on its grid can move:

{{still}}

For a still scene, the finished grid is computed once and kept in still_grid. Each later frame copies it back and redraws only the sun glow's bounding box. If the ASCII look is on too, the whole text screen is cached as well (still_screen), and each frame only restores the rectangles it drew over last time (glitches and tears) before drawing this frame's.

Those rectangles are returned to the window code, which passes them on to the system compositor so it copies only those parts to the screen. On a 4K screen a full frame is 33 MB, so this matters. Two tests (still_frames_match_full_render and partial_frames_match_full_render) render the same scenes both ways, with and without the shortcuts, and require every pixel to match.

The slideshow

A Player holds the scene on screen (cur), the next one once it has loaded (next), and, while a load is running, the receiving end of a channel (loading) through which the loader thread will deliver it.

The first picture

When a player starts there is nothing to show yet, so the first scene is built right away, on the calling thread. If the first file is broken it tries the next, so one bad file doesn't leave a black screen. Then it starts loading the one after in the background:

{{player_new}}

Loading in the background

Decoding a 4K JPEG and building its scene takes 50 to 300 ms, which is several frames. So every later scene is built on its own short-lived thread:

{{request}}

move || means the thread takes ownership of everything it uses: its own copies of the settings, the screen size and the seed. It shares nothing with the player, so no locks are needed. A plain std::thread is used instead of the rayon pool so that one long decode can't hold up the pool that draws frames. If the user presses an arrow key and the player moves on, it simply drops its end of the channel; the thread finishes, its send fails quietly, and the result is thrown away.

Each frame, the player checks the channel without waiting (try_recv):

{{recv}}

A loader that panics drops its sender, which shows up here as Disconnected and is handled like a file that failed to load: skip to the next one. After a whole lap of failures it stops trying and keeps showing what it has. When every file fails from the start, the screen shows the error message instead of staying black.

Transitions

When the current landscape has been on for its display time and the next one is ready, a transition starts. During it, both scenes are rendered in full into two scratch buffers (buf_a, buf_b), and blend mixes them row by row in parallel: crossfade, dissolve (blocks chosen by hash2), a soft ragged wipe, slide, pixelate (blocks grow on the old picture, then shrink on the new) or fade through black. Both scenes keep animating underneath. Progress goes through a smoothstep curve so it eases in and out.

The scratch buffers are two whole screens (16 MB at 1080p), so they only exist while a transition runs:

{{trans_end}}

Windows and timing

saver.rs handles every mode that uses ordinary windows: the full-screen screensaver on every monitor, the Windows preview box, a plain window, the Windows wallpaper, and the single full-screen window that Omarchy starts per monitor. It uses two libraries: winit to open windows and receive keyboard and mouse events on every platform, and softbuffer to put a buffer of pixels into a window without any GPU API.

winit runs an event loop and calls about_to_wait whenever it has handled all pending events and is about to sleep. That is where nynex decides when the next frame is due:

{{timing}}

ControlFlow::WaitUntil tells the operating system to wake the program at that time, and it uses no CPU until then. If drawing fell behind (the machine was busy, or the laptop was asleep), the schedule restarts from now instead of rushing to draw every missed frame. Windows covered by a maximised window are skipped altogether.

The rest of the file handles input. Left and Right step through the landscapes; any other key, a click or a wheel turn closes the screensaver. Mouse movement only counts once the pointer has moved more than 24 pixels from where it was when the screensaver became "armed" a moment after starting, because windows moving into place and high-resolution mice report tiny moves that shouldn't wake you. For the preview box, the program also checks every frame that the parent window still exists, and quits when Windows closes the Settings dialog.

15

The Wayland wallpaper

On Linux, --wallpaper doesn't use winit. A wallpaper has to sit under all windows on every monitor, which ordinary windows can't ask for on Wayland. The wlr-layer-shell protocol, supported by Hyprland, Sway, niri and other wlroots-style compositors, lets a program place a surface on a layer of the desktop. layer.rs puts one on the "bottom" layer of each monitor, with no keyboard or mouse input, and follows monitors as they are plugged in and out.

Instead of a timer it uses the compositor's frame callbacks. After each frame, it asks the compositor "tell me when it's a good time to draw the next one". The compositor answers when the screen is about to refresh, and doesn't answer for a surface that can't be seen, for example behind a full-screen window. So the wallpaper stops drawing without any extra code:

{{frame_cb}}

Frames are written into shared memory buffers (wl_shm) that the compositor reads directly. Up to three are kept, because the compositor may still be showing one while the next is being filled. A buffer that comes back from the compositor is several frames out of date, so the code keeps a short history of what changed in each recent frame, and copies into the reused buffer only the rectangles changed since it last held a frame. Then it tells the compositor which parts changed:

{{wl_damage}}

The settings app stops a running wallpaper by creating a file called wallpaper.stop in the settings folder; the wallpaper checks for it twice a second, deletes it and exits. (On Linux it also exits on SIGTERM or when the compositor goes away.) That works the same on Windows and Linux and needs no process IDs or signals.

16

Becoming the screensaver

Windows

A Windows screensaver is a normal .exe with a .scr extension. Windows runs whatever path is stored in the registry value HKCU\Control Panel\Desktop\SCRNSAVE.EXE. When you click "Use as my screensaver", install.rs copies the running program to %APPDATA%\nynex-screensaver\nynex.scr, writes that value, and sets the timeout and "screensaver on" flag with the SystemParametersInfoW API, which also tells Windows the setting changed. No administrator rights are needed, because it is all under the current user.

The Windows wallpaper uses a long-known trick: sending the undocumented message 0x052C to the desktop's Progman window makes Explorer create a separate window layer between the wallpaper and the icons. nynex finds that layer and makes its own windows children of it. Windows 11 24H2 reorganised these windows, and wallpaper.rs handles both layouts. When the wallpaper stops, it asks Windows to redraw the normal wallpaper so no frozen frame is left behind.

Omarchy

Omarchy's idle service runs a command named omarchy-launch-screensaver. The installer (in the separate omarchy-pixelbook-go repository) puts a script with that name in /usr/local/bin, which comes before /usr/bin on the PATH. That script starts nynex --screensaver --app-id org.omarchy.screensaver on every monitor. Using Omarchy's own app id means Omarchy's existing window rules (full screen, no animations) and its lock timer apply to nynex unchanged. If you turn nynex's screensaver off in settings, omarchy.rs writes a marker file and the script hands over to Omarchy's original screensaver instead.

Settings on disk

All settings live in one JSON file, read and written with the serde library, which generates the conversion code from the type definitions. Loading is defensive:

{{load_from}}

A file that doesn't parse is copied aside to config.json.bad before the defaults are used, so pressing Save afterwards can't silently erase a landscape list that only had a typo in it. Then sanitize clamps every number to the range the sliders allow, with a little headroom, so a hand-edited file can't ask for a billion birds, a zero-length frame or a NaN (the fin helper replaces non-finite numbers with the default).

Saving writes a temporary file and renames it over the real one. On every common file system a rename is atomic, so a crash or power cut mid-save leaves either the old file or the new one, never half of each:

{{save}}

Photos you add are copied into a landscapes folder next to the config, so moving or deleting the originals doesn't break the slideshow. Stills over 3,840 pixels are stored as a downscaled JPEG, since nothing on screen needs more.

Memory

Roughly what one 1080p screen holds:

WhatSizeWhen
The buffer the window shows8 MBalways (owned by softbuffer or the compositor)
Current scene: grid, tables, masks, caches2 to 10 MBalways; a still ASCII scene also caches a full screen (8 MB)
Next scene, waitingthe same againbetween loads and transitions
Transition frames16 MBonly during a transition
Decoded photoup to 20 MBonly while the loader builds a scene

On Linux, freed memory doesn't automatically go back to the system: glibc keeps it for reuse. After a landscape change and after each transition, the player calls trim_heap, which asks glibc to release whatever it is holding but not using:

{{trim}}

With that, the two-arena limit from startup, and the transition buffers that only exist during transitions, the memory the Linux wallpaper holds most of the time went from about 130 MB to about 75 MB. The measurements and the method are in BENCHMARKS.md.

Unsafe code

Rust checks memory safety at compile time, except inside blocks marked unsafe, where the programmer takes responsibility. nynex has 20 such blocks, and every one is a call into an operating-system API that Rust can't check:

FileBlocksWhat they call
install.rs6The Windows registry, short file names, and SystemParametersInfoW (screensaver on/off and timeout)
wallpaper.rs6Finding the desktop windows, the 0x052C message, re-parenting, restoring the wallpaper
saver.rs5Cursor position, the foreground window's size, and the preview box's parent window (its size, whether it still exists, and opening a child window inside it)
main.rs2glibc's mallopt and malloc_trim
layer.rs1poll: waiting on the Wayland connection with a timeout, so the stop file is still checked while no frames are wanted

The renderer, the slideshow and the settings code contain none. Each block has a // SAFETY: comment saying why the call is sound, which is the convention reviewers look for.
